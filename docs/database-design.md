## 1. Conventions

| Topic | Convention |
|---|---|
| Schemas | One per module (architecture §4.2): `identity`, `users`, `properties`, `assets`, `availability`, `pricing`, `booking`, `payments`, `ledger`, `payouts`, `access`, `charging`, `notifications`, `reviews`, `trust`, `disputes`, `platform`. `pgboss` is owned by the job library. |
| Naming | `snake_case`, plural table names, `<table>_<cols>_<type>` for indexes and constraints (`_ix`, `_uq`, `_gix`, `_fk`, `_ck`) |
| Primary keys | `uuid`, **UUIDv7** generated by the application (time-ordered and non-enumerable, R-19). Append-only high-volume logs (`*_events`, `ledger.entries`, `outbox`) use `bigint GENERATED ALWAYS AS IDENTITY` internally and are never exposed publicly. |
| Foreign keys | Always declared within a schema. **Across schemas they are declared too** (one database, integrity matters more than theoretical extractability), `ON DELETE RESTRICT` by default. Never `CASCADE` on business data. |
| Statuses | `text` + `CHECK (status IN (...))`, mirrored by TypeScript string-literal unions. A CI test asserts that each CHECK list equals its TypeScript enum. Native `ENUM` types were rejected: removing or renaming values is painful. |
| Money | `bigint` paise (`*_paise`), `CHECK (>= 0)` unless the column is a signed adjustment. Currency is implicit INR at pilot. A `currency char(3)` column exists on payments, payouts and journals for future use. |
| Time | `timestamptz` everywhere (UTC). Periods are `tstzrange`, **half-open `[)`, non-empty**, enforced by `CHECK`. Local wall-clock rules are `time` + `smallint[]` weekdays + an IANA `timezone` text on the property. |
| Timestamps | `created_at timestamptz NOT NULL DEFAULT now()`. Mutable tables also get `updated_at` (a trigger keeps it current). |
| Optimistic concurrency | `version integer NOT NULL DEFAULT 1` on mutable aggregates edited by humans (assets, policies, rates, series, disputes). Updates use `WHERE id = $1 AND version = $2`. Zero rows → `409 conflict.stale`. |
| JSON | `jsonb` only for snapshots (price lines, policy snapshots), provider payloads and type-specific attributes validated by Zod. Never for data that's queried relationally. |
| Encrypted fields | `<name>_enc bytea` (AES-256-GCM envelope ciphertext, D-037). If lookup is needed, `<name>_hmac bytea` (keyed HMAC blind index) with a unique or regular index. |
| Booleans | `NOT NULL` with defaults. No three-valued booleans. |

## 2. Soft deletion and lifecycle

- **No generic `deleted_at` on business entities.** Business entities have explicit lifecycle states (`ARCHIVED`, `CLOSED`, `REMOVED`, `ENDED`) from the domain model. Bookings, payments, ledger entries, disputes and reviews are **never** deleted.
- **Hard delete** only for ephemeral or derived data: expired OTP challenges, expired sessions, consumed idempotency records past TTL, published outbox rows past retention, rate-limit buckets.
- **PII erasure** (DPDP rights, account closure) = **anonymisation in place**: encrypted PII columns nulled or replaced with tombstones, HMACs removed, display names replaced. Rows stay for financial and legal records. Implemented as an audited job.
- **Media** (`assets.asset_media`) has `removed_at`. The object is deleted from storage by the retention job.

## 4. Statuses

Every state machine in domain-model §5 maps to one `status text` column with a `CHECK` listing exactly its states. **Transitions are enforced in application code** (pure state-machine module, unit-tested over the full transition table). The DB enforces the **value set** and the invariants that must hold regardless of code: no overlap, one open issue, balanced journals, one review per direction, refunds ≤ captured. Each transition writes a `*_events` history row in the same transaction.

## 5. Geographic queries (Phase 10)

> **As built (migration 0004):** discovery reads only the views `discovery.published_listings`, `published_rates`, `public_photos` and `published_availability_rules`. They have no exact-location, address, access-instruction or owner-id columns, and they filter to PUBLISHED listings of ACTIVE hosts at NOT_REQUIRED/PARTICIPATING properties. The radius predicate through the view uses `properties_public_point_gix` (tested with `EXPLAIN`). Added `rates_live_mode_price_ix` for mode and price filters. Search takes up to 500 candidates, then filters availability and paginates in the app (D-077).

- `properties.public_point geography(Point,4326)` with a **GiST index** ★ (validated: `ST_DWithin` uses `properties_public_point_gix`, check C13).
- The search query shape:

```sql
SELECT a.id, ST_Distance(p.public_point, $origin) AS distance_m
FROM assets.assets a
JOIN properties.properties p ON p.id = a.property_id
WHERE a.status = 'PUBLISHED' AND a.asset_type = $type
  AND p.participation_status IN ('NOT_REQUIRED','PARTICIPATING')
  AND ST_DWithin(p.public_point, $origin, $radius_m)
  -- type filters (covered, connectors && $connectors, power_kw >= $min, …) via joins to detail tables
ORDER BY p.public_point <-> $origin      -- KNN, index-assisted
LIMIT $candidate_limit;                  -- then the availability filter for the window, then paginate
```

- Exact points are **encrypted and never queried in SQL** (L-2). V-GEO compares decrypted points in the application.
- Supporting indexes: `assets (status, asset_type)`, `charger_details USING gin (connectors)`, `parking_details (covered, max_vehicle_class)`.
- **Availability filtering for search:** candidate assets (≤ a few hundred at pilot) → a bulk "units with no holding booking overlapping the window" query (GiST on `bookings (unit_id, blocked_period)` via the exclusion index) + rule and exception evaluation in the application. Revisit with a precomputed availability table only if p95 search exceeds the SLO (architecture §14).
- Cursor pagination on `(distance_m, id)` for stable ordering.

## 6. Booking concurrency (the critical design) ★

### 6.1 Constraint

```sql
holds_unit     boolean GENERATED ALWAYS AS
                 (status IN ('AWAITING_HOST_APPROVAL','PENDING_PAYMENT','CONFIRMED','IN_PROGRESS')) STORED,
blocked_period tstzrange NOT NULL,   -- [start, end + buffer_minutes), set by BEFORE trigger
CONSTRAINT bookings_no_overlap
  EXCLUDE USING gist (unit_id WITH =, blocked_period WITH &&) WHERE (holds_unit)
```
- **One-sided buffer** (`[start, end + buffer)`) gives the required gap of exactly `buffer` between consecutive bookings. A two-sided buffer would double it. The buffer is **snapshotted** per booking, so a host changing the buffer never invalidates existing bookings.
- **Prototype finding #1:** `blocked_period` **can't be a generated column**. `timestamptz + interval` isn't `IMMUTABLE` in PostgreSQL. It's set by a `BEFORE INSERT OR UPDATE OF period, buffer_minutes` trigger.
- Half-open and non-empty periods are enforced by `CHECK (NOT isempty(period) AND lower_inc(period) AND NOT upper_inc(period))` (C7).

### 6.2 Lapsed holds (R-40)
The constraint predicate can't reference `now()`, so a `PENDING_PAYMENT` row past `hold_expires_at` still blocks at constraint level until its status changes (validated, C4). Therefore the booking transaction, before inserting, runs:

```sql
UPDATE booking.bookings SET status = 'EXPIRED'
 WHERE unit_id = ANY($candidate_units) AND status = 'PENDING_PAYMENT'
   AND hold_expires_at < now() AND blocked_period && $requested_blocked_period;
```
The same applies to `AWAITING_HOST_APPROVAL` past `approval_expires_at`. The `expire-holds` job (architecture §7) tidies the rest. All read-side availability queries also exclude lapsed holds (D-036).

### 6.3 Property outsider cap (BR-06, R-39)
- A per-unit constraint can't enforce a cross-asset cap. **Prototype finding #2 (C16-control):** without serialisation, two concurrent transactions both see "1 of 2" and both insert. **The cap is breached.**
- Design: for a property with `outsider_cap` set, the booking transaction takes `SELECT … FROM properties.properties WHERE id = $p FOR UPDATE` **before** the cap check and the insert. Concurrent bookings in the same capped property serialise. Properties without a cap don't take the lock (no contention for commercial lots).
- The cap check uses **maximum simultaneous** holding bookings over the requested range (`booking.max_concurrent_in_property`, a sweep over start points), not the total count of overlapping bookings. The total count would wrongly refuse non-simultaneous bookings (C8a/C8b).

### 6.4 Transaction outline (isolation: READ COMMITTED + explicit locks + constraint)

```
BEGIN;
  [if capped] SELECT 1 FROM properties.properties WHERE id=$p FOR UPDATE;
  SELECT 1 FROM assets.assets WHERE id=$a FOR SHARE;                -- vs. host BLOCK inserts (§7)
  expire lapsed holds overlapping candidate units (6.2);
  [if capped] assert max_concurrent_in_property($p, $blocked) < cap;
  pick the first free unit (ordered by label) → INSERT booking;   -- exclusion constraint protects the race
     on exclusion_violation: SAVEPOINT-retry with the next free unit (bounded), else 409
  INSERT booking_events, outbox, idempotency record;
COMMIT;
```
**Lock order is fixed: property → asset → booking rows** for every transaction that takes more than one (booking create, host block, cancellation), which prevents deadlocks. SERIALIZABLE isolation was considered and rejected for this path: the exclusion constraint plus the explicit property lock give the guarantees with predictable contention and no retry storms.

### 6.5 Idempotency
`UNIQUE (customer_id, idempotency_key)` on bookings (C5) **plus** `platform.idempotency_keys` for the HTTP replay of the original response. The DB unique key is the backstop if the HTTP layer fails between commit and storing the response.

**As built (Phase 12, D-095):** the unique key plus the quote's `FOR UPDATE` lock. A parallel retry waits on the quote lock, sees it used by a booking with the same key and returns that booking; a sequential retry finds it before the transaction. `platform.idempotency_keys` is deferred until payments need byte-identical replay.

### 6.6 As built (Phase 12)
- `booking.create`: preview reads (quote, asset context, own-listing check) **before** `BEGIN`; inside: quote `FOR UPDATE` → property (`FOR UPDATE` if capped) → asset `FOR SHARE` → lapsed holds on the candidate units `FOR UPDATE` → `EXPIRED` (with SYSTEM events) → engine re-check on the transaction (rules, exceptions, reservations) → cap via `maxConcurrent` → insert under `SAVEPOINT`, next unit on `bookings_no_overlap` → quote used → event + audit. **Every query runs on the transaction** (D-096).
- Transitions (approve, decline, cancel, payment) lock the booking row `FOR UPDATE`, read its *effective* status (a lapsed hold is `EXPIRED`), apply the pure state machine and write a `booking_events` row; refunds are computed from the locked row.
- Jobs (pg-boss, D-097) select with `FOR UPDATE SKIP LOCKED` in batches of 500.
- Tested under real concurrency: 6 customers × 1 unit → 1 booking; 5 × 3 units → 3; 4 × cap 2 → 2; parallel same-key → one booking.

## 7. Availability storage

> **As built (Phase 11, migration 0005):** `availability.availability_exceptions` (BLOCK/OPEN, asset-wide or per unit, half-open `tstzrange`, GiST on (asset_id, period), host-only reason). Discovery reads `discovery.published_units` (ids only) and `discovery.published_availability_exceptions` (no reason or author); `published_listings` gained `buffer_minutes`. The pure engine (`availability/domain/engine.ts`) computes availability; reservations come through `ReservationSource` (Phase 12). Block-vs-booking locking as below is implemented on the block side and tested.
- Rules (weekday and time windows, valid dates) and exceptions (BLOCK and OPEN ranges) are stored as data. Expansion to instants happens in the application in the asset's timezone (Luxon, BR-03).
- **Host block vs booking (BR-04):** a BLOCK exception insert runs in a transaction that locks the asset row (`FOR UPDATE`) and checks for overlapping holding bookings on the affected units. Booking creation takes the same asset lock (`FOR SHARE`) while checking exceptions, so a block and a booking can't commit in conflict. Cheap at pilot volumes.

## 8. Payments, ledger and reconciliation (Phases 15–16)
- **Webhook dedupe:** `provider_events UNIQUE (provider, event_id)` (C11). Processing marks `processed_at`. Handlers are idempotent on the payment row (`SELECT … FOR UPDATE` on `payments`, transition only from an allowed state).
- **Payment-to-booking:** a payment can only confirm its own booking. The amount must equal `bookings.total_paise`, otherwise it's quarantined (`provider_events.quarantined_reason`).
- **Ledger:** double-entry with a **deferred balance check per journal** (C9) and **append-only entries** (C10). Every journal carries an `idempotency_key` (for example `payment:{id}:capture`), so retries can't double-post.
- **Standard journals** (amounts from the booking snapshot):

| Event | Debit | Credit |
|---|---|---|
| Payment captured | `customer_clearing` (total) | `platform_revenue_service_fee`, `tax_payable_gst`, `platform_revenue_commission`, `society_payable:{p}`, `host_payable_pending:{h}` |
| Gateway fee (from settlement) | `gateway_fees` | `customer_clearing` |
| Earnings released (BR-18) | `host_payable_pending:{h}` | `host_payable_available:{h}` |
| Payout created / paid | `host_payable_available:{h}` → `host_payable_in_payout:{h}` | then `in_payout` → `cash_settlement` on PAID |
| Refund before release | reverse the capture lines proportionally | `customer_clearing` |
| Refund after payout (BR-19) | `host_receivable:{h}` | `customer_clearing` |

- **Reconciliation:** `settlement_lines` imported daily, matched to `payments` by `provider_payment_id`. Unmatched items or amount differences become `reconciliation_items` (finance queue A-05). A nightly job recomputes `account_balances` from entries and alerts on drift.
- Exact tax lines depend on the CA review (Phase 15). The structure supports any number of tax accounts.

## 10. Audit strategy
1. **Domain history tables** (`booking_events`, `dispute_events`, payment status history in `provider_events` + `payments`): every state transition, in the same transaction, append-only (C14).
2. **`platform.audit_events`:** admin actions, sensitive user actions (payout account change, policy change, verification decisions, restrictions), with redacted before and after and a reason. Append-only via trigger **and** grants.
3. **`platform.pii_reveals`:** every admin reveal of masked PII.
4. **Ledger:** immutable by design. Corrections are reversal journals.

## 11. Encryption, PII and retention

| Data | Storage | Lookup |
|---|---|---|
| Phone, email | `_enc` + `_hmac` | HMAC unique |
| Exact address and point | `_enc` | none (only by property ID) |
| Access instructions | `_enc` | none |
| Vehicle plate | `_enc` + `_hmac` | HMAC (guard lookup, uniqueness) |
| Payout details | `_enc` + `_hmac` | HMAC (shared-account signal) |
| KYC provider references, legal names, PAN | `_enc` | none |
| OTP codes, session tokens, access codes, guard tokens | **hash only** (SHA-256 for random tokens; keyed HMAC for short codes) | hash |

Key hierarchy: KMS master key → per-purpose data keys (address, plate, phone, payout, KYC), rotated yearly. The ciphertext carries a key version for re-encryption jobs. HMAC keys are separate from encryption keys.

The retention schedule (trust-and-safety.md §14) is implemented by `retention-purge` with per-table policies. **Plate masking after 30 days** = the host and property-admin views stop showing plates through response shaping. The stored encrypted plate is kept for dispute and financial windows and then cleared.

## 13. Migrations and evolution
- Plain SQL files, forward-only, numbered and timestamped, applied by the release step (architecture §12).
- **Expand → migrate → contract** for breaking changes. `CREATE INDEX CONCURRENTLY` for large tables. New `CHECK` constraints added `NOT VALID` then validated.
- Adding a status value = update the CHECK + the TypeScript union in the same release. The consistency test fails otherwise.
- **Partitioning:** none at pilot. Candidates when volume justifies: `access_events`, `audit_events`, `notifications`, `outbox`, `booking_events` (monthly range partitions), and `bookings` by time if it grows past tens of millions of rows.
- New asset type (domain-model §8) = seed a row in `asset_types` + one detail table migration. No change to booking, payment or ledger tables.

## 14. Validation results

The prototype lives at [db-prototype/schema.sql](db-prototype/schema.sql), with checks in [db-prototype/checks.sql](db-prototype/checks.sql) and a runner in [db-prototype/run-checks.sh](db-prototype/run-checks.sh). The runner starts a throwaway PostGIS container and runs two-session races. Run 2026-10-19 on PostgreSQL 17.5 + PostGIS 3.5: **all 17 checks pass (18 PASS assertions, 0 FAIL).**

| Check | Proves | Result |
|---|---|---|
| C1 | Overlapping booking on the same unit is rejected (exclusion constraint) | PASS |
| C2 | Adjacent bookings with zero buffer are allowed | PASS |
| C3 | 15-minute buffer: 10:10 rejected, 10:15 accepted | PASS |
| C4 | A lapsed hold blocks until expired in-transaction, then the unit is re-bookable | PASS |
| C5 | Duplicate idempotency key rejected | PASS |
| C6 | A cancelled booking frees the unit | PASS |
| C7 | Non half-open range rejected | PASS |
| C8a/b | Cap uses maximum simultaneous bookings, not the total overlapping count | PASS |
| C9 | Unbalanced ledger journal rejected at commit | PASS |
| C10 | Balanced journal accepted; entries are append-only | PASS |
| C11 | Duplicate provider webhook event rejected | PASS |
| C12 | Active-plate uniqueness; re-add after removal allowed | PASS |
| C13 | Radius search correct and **uses the GiST index** | PASS |
| C14 | Booking history is append-only | PASS |
| C15 | **Real race:** two sessions insert overlapping bookings, the second blocks then fails, exactly one booking | PASS |
| C16 | **Real race under property cap:** with the property lock, the second session serialises and is refused | PASS |
| C16-control | The same race **without** the lock breaches the cap (proves the lock is necessary) | PASS (cap breached as predicted) |

**Findings that changed the design:**
1. `blocked_period` moved from a generated column to a trigger (immutability).
2. Property-cap serialisation by row lock is required, not optional (C16-control).
3. Test harness note: the PostGIS image reports ready during its temporary init server. Wait for the post-init "ready" log line (applies to Phase 7 local and CI setup).
