# Deploying to Render (staging)

This guide covers the private **staging** deployment of ParkBro on Render, defined in `render.yaml` (D-172).

Staging runs real production builds with the simulators instead of external providers, and is **invite-only**. Use it for demos, tester feedback and rehearsing operations. It is not the public launch: see `launch-checklist.md` for that.

| Area | In staging |
| --- | --- |
| Sign-in | Fixed 6-digit code (`OTP_DEV_FIXED_CODE`), only for numbers in `STAGING_ALLOWED_PHONES` |
| Payments | Built-in simulator; no real money |
| Place search and maps | OpenStreetMap: Photon search and OpenFreeMap tiles (no key, D-174) |
| Messages | Written to the API log (redacted), plus the in-app inbox |
| AI search | Rules parser (no model) |
| Search engines | `noindex` on web and admin; a "Test environment" banner on web |

## 1. What gets created

All resources are in the Singapore region:

| Resource | Plan | Purpose |
| --- | --- | --- |
| `parkbro-db` | PostgreSQL 17, basic-256mb | Database (PostGIS, btree_gist and pgcrypto are enabled by migration 0001). No internet access |
| `parkbro-api` | Web service, starter | API and scheduled jobs. Runs migrations on start. 1 GB disk at `/var/data` for photos |
| `parkbro-web` | Web service, starter | Customer and host app. Reaches the API over the private network (`API_INTERNAL_HOSTPORT`) |
| `parkbro-admin` | Web service, starter | Admin console, on its own origin |

The cost is roughly three starter services plus the smallest database. Check Render's current pricing. The disk needs a paid plan.

## 2. First deploy

1. Push the repo to GitHub. It is `github.com/riiken/ParkBro`.
2. In Render, go to **New → Blueprint**, pick the repo, and Render reads `render.yaml`.
3. Fill in the values marked `sync: false`:
   - **`FIELD_ENCRYPTION_KEYS`**: run `echo "v1:$(openssl rand -base64 32)"` and paste the output, including `v1:`. **Keep a copy somewhere safe.** If you lose it, the encrypted phone numbers, plates and addresses in the database can't be read.
   - **`STAGING_ALLOWED_PHONES`**: the testers' numbers, comma-separated, for example `9876543210,9123456789`. Include your own.
   - **`OTP_DEV_FIXED_CODE`**: a 6-digit code to share with testers. Don't use 246810, which is public in this repo.

   `BLIND_INDEX_KEY` and `OPS_MONITOR_TOKEN` are generated by Render.
4. Click **Apply**. The first build takes a few minutes. The API runs migrations before it starts, and its health check (`/api/health/ready`) only passes once the database is up to date.
5. Open the `parkbro-web` URL. You should see the yellow "Test environment" banner.

## 3. Make yourself an admin

1. Sign up on the **web** app with your allowlisted number and the fixed code.
2. In Render, open **parkbro-api → Shell** and run:

   ```bash
   node apps/api/src/cli/grant-admin.ts <your 10-digit number> SUPER_ADMIN
   ```

3. It prints an `otpauth://` link **once**. Add it to an authenticator app: Google Authenticator, 1Password, Authy or similar.
4. Open the `parkbro-admin` URL and sign in with your number, the fixed code, then the authenticator code.

## 4. Optional: sample data for a demo

The seed creates two hosts, a customer, an admin and four listings in Koramangala and HSR Layout.

1. Add the seed phones to `STAGING_ALLOWED_PHONES`: `9000000001,9000000002,9000000003,9000000009`.
2. Redeploy.
3. In the API shell, run:

```bash
node apps/api/src/cli/dev-seed.ts
node apps/api/src/cli/dev-admin-code.ts   # the sample admin's current authenticator code
```

## 5. Monitoring

| What | How |
| --- | --- |
| Health | Render restarts services whose health check fails |
| Uptime and alerts | Point an uptime monitor (Render, UptimeRobot, Better Stack…) at `https://<api-url>/api/health/ops` with the header `Authorization: Bearer <OPS_MONITOR_TOKEN>`. It returns **503 when anything is critical**. The same checks appear on the admin dashboard |
| Logs | **parkbro-api → Logs**: structured JSON with request IDs. Simulated messages (`[messaging:…]`) appear here too |

## 6. Updating

Every push to the default branch redeploys the services. Migrations run automatically on API start, and they are forward-only. The Blueprint keeps its settings: change environment variables in the dashboard or in `render.yaml`.

## 7. Moving from staging to the real launch

Each external piece replaces a simulator. The API then lets you turn `STAGING` off.

| Step | Change |
| --- | --- |
| SMS/WhatsApp provider registered | Add its adapter; set `OTP_PROVIDER` and `MESSAGING_PROVIDER`; remove `OTP_DEV_FIXED_CODE` |
| Razorpay live | `PAYMENT_PROVIDER=razorpay` with live keys; set the webhook URL to `https://<web-url>/api/v1/webhooks/payments/razorpay` |
| Maps | Already live with OpenStreetMap (D-174); optionally switch to a paid provider later |
| Database TLS | `DATABASE_SSL=no-verify` (or `require`). Production refuses `disable` |
| Domains | Custom domains for web and admin (separate subdomains, for example `admin.`) |
| Go live | `STAGING=false`, remove `STAGING_ALLOWED_PHONES`, and set `PILOT_CUSTOMER_CLEARANCE=true` for the controlled pilot |

The API refuses to start in production while any simulator is still configured.

## 8. Known limitations of this setup

- **Real client IPs.** The API sits behind the web app's server-side proxy. Rate limits per IP may see the proxy, not the customer (R-89). Staging is invite-only, so this matters only for the real launch, where the edge must forward the client IP.
- **Photos.** They live on one disk attached to one API instance. Move to object storage (S3 or R2) before running more than one API instance.
- **Region.** Render has no India region; Singapore is the closest.
